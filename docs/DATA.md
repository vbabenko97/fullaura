No personal photographs or generated personal previews are included in this repository. `backend/data/catalog.json` holds product facts, without images, from the sources in the register below. The landing page uses local system fonts and CSS, with no third-party imagery. `docs/assets/t04-preferences-desktop.png` and `t04-preferences-mobile.png` are screenshots of FullAura's own planning screen during T-04, showing a scripted plan of catalog facts; they hold no product photo, personal photo or model output.

The tests use `tests/fixtures/synthetic_catalog.json`, a catalog invented for testing and marked `"synthetic": true`. Its products, prices, retailer and links are fictional, and its links use the reserved test domain `synthetic.example`. It is not a catalog source: it stays out of the container image and must not appear in the interface or a demo as real products.

Keep private inputs and outputs in ignored `data/private/` while testing. Obtain the subject's permission for model processing separately from permission to publish a demo image. The local planning screen uses a local font stack and no third-party imagery.

## Photo handling for upload support

This accepted policy is defined by [D-31](DECISIONS.md#d-31-no-persistent-server-copies-of-personal-photos). In the closed beta, `/api/previews` serves invited sessions whose invite has agreed to the photo notice ([D-44](DECISIONS.md#d-44-the-betas-try-on-is-experimental-and-does-not-wait-for-t-02)). It refuses a request before reading its body when the session, the photo consent, the plan token, the look, the quota or the budget does not allow it. Before upload, the browser redraws each photo, JPEG, PNG or WebP, as an upright JPEG of at most 2048 pixels on its longer side, which drops its metadata; the photos never leave the browser in their original form.

The multipart request carries only the two photos; the server writes the prompt from the checked look. It is parsed incrementally into bytearrays; it does not use Starlette's disk-spooled upload files. The processor accepts upright JPEGs only and removes metadata again before sending them to a provider. It rejects a JPEG whose visible orientation depends on EXIF orientation metadata, because removing that tag without rotating the encoded pixels would change how the photo appears. It may keep the recognized JFIF header and Adobe color-transform field, a complete ICC profile, and JPEG coding tables. It removes Exif, XMP, IPTC, comments and data appended after the primary JPEG image. Each input is limited to 10 MiB; the server's prompt to 3000 bytes; generated previews to 16 MiB.

FullAura will keep no persistent server copy of an original photograph, generated preview or provider response. During one request, it may hold the original, stripped input and preview bytes only in memory. It must not write them to logs, caches, backups or a database. The response returns the preview to the browser without server-side storage. This rule cannot establish or shorten a model provider's retention; the photo-processing notice must describe the provider's current terms separately.

The upload path must clean up in this order on success and failure:

1. Discard the original and metadata-stripped bytes after the provider request ends.
2. Discard a preview if returning it to the browser fails, image validation fails, or the provider returns an error or times out.
3. Delete every request-specific temporary file in `finally`, including partial uploads and partially written previews. Error logs may retain a request ID, error class and timing, but never image bytes, image URLs or a full personal profile.

One monotonic 120-second deadline covers the multipart upload, provider attempts and retry waits. The HTTP client cancels its request at the deadline. The server also monitors the request for disconnects and cancels the provider task when the browser leaves. It clears both input buffers in `finally` after provider success, provider error, timeout, disconnect or input validation failure. It clears the generated preview after the response succeeds or its connection fails. The implementation uses memory only and creates no temporary files, so it has no request files to sweep at startup. If a later implementation writes temporary files, it must isolate each request in a private temporary directory, delete that directory before responding, and remove leftovers from interrupted earlier processes during startup before accepting uploads. If either cleanup or the startup sweep fails, photo processing stays blocked until cleanup succeeds. Tests for that implementation must cover interrupted writes, cleanup failures and startup-sweep failures.

## Pilot records

The closed beta keeps a few records in a private Azure Blob Storage container that only the app's managed identity and the operator can read ([D-43](DECISIONS.md#d-43-an-invite-only-beta-replaces-the-anonymous-demo)): for each invite, when it confirmed age 18 or older and agreed to the photo notice, its request counts and the IDs of its feedback; the shared spending ledger; a record of each model call with its kind, outcome, reserved and actual cost and times; and the feedback answers, including what a participant noticed in a try-on when they choose to say. A call record written by a revision with [D-52](DECISIONS.md#d-52-a-call-record-keeps-its-outcome-apart-from-its-cost-and-the-pilot-report-counts-invites) keeps the outcome, such as a timeout or a cancelled try-on, apart from whether the cost is known, and an invite's record also counts the planning requests that no plan could meet, by the rules that ruled them out, with the random operation IDs of the last 20 so that a repeat counts once. A record written by an earlier revision, including one still running while a deployment overlaps, has neither; if its cost was unknown it says only "unknown" and not what happened ([D-52](DECISIONS.md#d-52-a-call-record-keeps-its-outcome-apart-from-its-cost-and-the-pilot-report-counts-invites)). Invites appear only as the first 16 hex digits of their code's digest. The records hold no photo, try-on, plan, preference, profile, provider response or invite code. A scheduled job deletes every record on 2026-11-09 from 10:00 Vienna time, after the pilot ends, and the beta closes then ([D-49](DECISIONS.md#d-49-a-scheduled-job-deletes-the-pilot-records-and-the-beta-closes-then)). Before deleting, the job writes a marker that holds only when the deletion began and the purge time, and keeps it, so the app writes nothing afterwards, provided its requests reach storage within about a minute ([D-50](DECISIONS.md#d-50-a-closure-marker-and-a-grace-period-keep-writes-from-outliving-the-purge)); a lifecycle rule that deletes each record 30 days after its last change stays as a backstop. A participant can delete their feedback at any time. [BETA.md](BETA.md) describes what participants are told.

Plans saved by a participant stay in their own browser's storage, with their shopping list and without photos or try-ons, until they delete them.

## Model providers

Planning sends a participant's preferences and owned-item descriptions to Muse Spark through Baseten's synchronous Model APIs. Baseten's [Model APIs documentation](https://docs.baseten.co/inference/model-apis/overview), checked on 2026-10-31, says: "For synchronous Model API requests, Baseten doesn't store inputs or outputs under its zero data retention policy." Its [security practices](https://www.baseten.co/security-practices/) of 15 September 2026 say the same and allow a customer to change it by written notice. The [limits page](https://docs.baseten.co/inference/model-apis/pricing-and-limits) says usage counts are kept for 92 days, and the Model APIs page says the regions that serve a shared model can change. These are Baseten's published terms, not a check of FullAura's account. Baseten's [terms](https://www.baseten.co/terms-and-conditions/) count models served through Model APIs as third-party products, whose providers "may have access to Customer Content"; whether that applies to Muse Spark Open, which Baseten serves itself, only Baseten can confirm. The participants' data notice says what the documentation says and that it is not an account check. The experimental Design My Look mode, when it is switched on, sends the style goal, colors, occasion, season, budget, clothing line, garment types, shoe choice and material exclusions, without sizes or owned items, and then its concept with the catalog products in the person's sizes, whose IDs name the size. The server keeps the latest concept in memory for up to a day, as it does the latest plan. Meta's terms for the try-on are covered in [D-07](DECISIONS.md#d-07-standard-mode-for-personal-photographs). Every request to Muse Image turns off the generator's own web search, image search and code tools (`tool_enablement`, [D-60](DECISIONS.md#d-60-a-try-on-turns-off-the-image-models-own-web-and-image-search)), so a try-on works only from the two photos and FullAura's text.

The shopping agent sends what a person types, their budget and their clothing line to Muse Spark on Meta's API in Standard mode, where Meta does not train on the content; their sizes stay on FullAura's server.

## Catalog sources

For each catalog source, record the permission or license, source URL, retrieval time, allowed image use, and any required attribution. Public accessibility alone does not establish reuse rights. Product facts and product images need different rights ([D-25](DECISIONS.md#d-25-product-facts-and-product-images-need-different-rights)). For facts such as price, composition and delivery, record what the source's terms of use allow and the date you checked them; record facts for a few products by hand rather than copying the site's catalog. For images, record the license, the feed whose terms permit display, or that FullAura took the photo. Each variant and offer must retain its source and the time its data was last checked; missing size, composition, or stock data remains unknown.

A catalog file follows the record format in `backend/app/catalog.py` and lives under `backend/`, because the container image leaves out `data/`. Every field is present, and a value the source does not give is written as `null`. Keep the composition as the source shows it, word for word, in `source_text`. Name each component's material from the list in `backend/app/catalog.py`, which also accepts other common names such as PU; a file that uses any other material name is refused. Mark a composition `complete` only when the source names the material of every labelled part, each from the list ([D-27](DECISIONS.md#d-27-a-composition-is-complete-when-it-names-every-labelled-part)); a labelled part that is missing or named only vaguely, such as "Synthetik", makes it `partial`. When the source names a trim's material, such as metal buttons, record it as a component; a trim named vaguely, such as a zip "aus Plastik", stays in `source_text` only. Where the source gives percentages for every component of a part, they must sum to 100 ([D-23](DECISIONS.md#d-23-materials-are-compared-by-names-from-a-fixed-list)).

Record a product's clothing line only when the retailer states it, through a department tag or category such as "Herren", or text on the product page such as "für Damen und Herren", which makes it unisex; otherwise write `null`. Record a variant's comparable size in the system the retailer uses, without converting it, and `null` when the label fits no system ([D-36](DECISIONS.md#d-36-the-person-states-whom-the-looks-are-for)).

Each shoe's closure, closed or open, comes from the retailer's own product type, such as "Sneaker" or "Slide"; the Giesswein and GEA closures were added on 2026-10-30 from their product names and categories.

A catalog variant can carry a product photo only with a register entry that records the right to display it ([D-56](DECISIONS.md#d-56-a-variant-can-carry-a-photo-only-with-recorded-rights)). On 2026-10-31 no source below grants that right, so no variant has a photo and the "Allowed image use" column stays "None".

## Catalog coverage

The closed beta needs the catalog to serve a few typical wearers, so `tests/test_catalog_coverage.py` checks nine example profiles in three scenarios. The profiles are examples, not any person's sizes:

| Profile | Line | Sizes |
| --- | --- | --- |
| Men's S | men's | S, waist and length 30/32, EU shoe 41 |
| Men's M | men's | M, 32/32, EU shoe 42 |
| Men's L | men's | L, 34/32, EU shoe 43 |
| Men's XL | men's | XL, 36/32, EU shoe 44 |
| Women's XS | women's | XS, EU shoe 36 |
| Women's S | women's | S, EU shoe 38 |
| Women's M | women's | M, EU shoe 39 |
| Women's L | women's | L, EU shoe 40 |
| Women's XL | women's | XL, EU shoe 37 |

| Scenario | Budget | Exclusion |
| --- | --- | --- |
| Office in autumn | €250 per look | wool |
| Casual | €150 per look | none |
| Casual capsule | €300 for the whole plan | wool |

For each of the 27 cases, code must find three different complete looks with closed shoes in every look that pass every hard constraint, from catalog items alone, and at least one position that a different catalog item can fill while the plan still passes. A case that fails is a catalog gap, to be closed with sourced records and never by relaxing a constraint or inventing data. The search combines the 60 cheapest looks of each case.

Women's M with EU shoe 41 is a 28th case, in the casual scenario only, because no women's shoe in EU 41 can pass a material exclusion. Of the 152 pages in Tom Tailor's sitemap on 2026-11-01 whose addresses name women's shoes, the 40 with EU 41 on sale all have a sole of thermoplastic elastomers or polyvinyl chloride. Neither is on the material list, so those compositions are partial, and the composition of the Tchibo sneaker names no parts.

Tests also check that women's M has a T-shirt, a long-sleeved top, a blouse and trousers, and that women's S, M and L each have two knitwear products and one outerwear product.

On 2026-11-01 all 28 cases pass, and a script that removed each product in turn, with all its variants, found every case still passing. Women's L under a wool exclusion has two Tom Tailor shoes in EU 40, the platform sneaker and the mesh sneaker, and a test checks that its three cases pass without the platform sneaker in EU 40 ([D-55](DECISIONS.md#d-55-a-second-closed-shoe-in-eu-40-keeps-womens-l-from-depending-on-one-pair)). Known risks:

- Every case needs Tom Tailor, and the men's cases also need Armedangels, which sells every men's top in the catalog, so losing either store breaks those cases.
- The men's casual cases fail if any two of their six cheapest products are gone: two Armedangels tops, two Tom Tailor chinos and two Tom Tailor sneakers. The office and capsule cases fail if both of their shoes are gone.
- Six shoe prices, one pullover's and two Armedangels women's bottoms' are sale prices, although the cases still pass at the regular prices. A sale size can sell out: on 2026-11-01 the page's stock data showed fewer than five pairs of the Sneaker mit elastischem Schaft in EU 41 and 44, the black Sneaker mit Plateau in EU 39 and the Sneaker mit Mesh-Einsatz in EU 36.
- Men's looks use the Armedangels tops. Only two of them fit a look at €150, so the men's casual looks repeat a top and differ in their chinos or shoes.
- On 2026-11-01 no plan with closed shoes exists for women's XXL, men's XS and XXL, women's EU 42 and 44 to 46, or men's EU 36 to 40, 45 and 46. Women's EU 43 has only the two GEA shoes, at €175 and €235.

The stores checked and rejected on the way are summarized in [D-47](DECISIONS.md#d-47-tom-tailor-and-tchibo-supply-affordable-basics-and-closed-shoes).
